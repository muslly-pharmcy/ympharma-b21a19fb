
- Oracle sync receiver is the TanStack route /api/public/oracle-sync (HMAC ORACLE_SYNC_HMAC_SECRET); no Supabase edge functions — project rule.
- ERP integration goes through /api/public/erp/v1/* (HMAC + idempotency, versioned snapshots, ERP_SYNC_ENABLED kill switch); legacy oracle-sync apply is frozen — it overwrote stock and mixed official/selling prices.
- Public backend identity is pinned in config/public-backend.ts; generated clients are redirected by the Vite resolver to app-owned lazy adapters to survive managed regeneration and prevent stale runtime overrides.
- Privileged access requires a securely bound URL, project ID and matching credential; never reuse a credential from another binding.
- SSR emits only public URL/key in escaped inert JSON before Scripts; session storage and public query/navigation caches are project-scoped, and private query/API responses are not persisted.
- Resolve server secrets in server-only modules; use createSelectedAdminClient for opaque secret keys, and never put a server secret in VITE_ variables or client configuration. Ordinary caller authentication uses fresh caller-scoped public-key clients.
- Private product-image operations require exact product organization and database upload/review permissions before privileged storage. Only canonical product-prefixed objects in product-images/catalog-media may be signed; public signing requires both approved public products and approved media. Keep expiring URLs out of durable records and query persistence.

## Agent skill routing and safe discovery

- Before editing YmPharma or muslly.com, select the existing task-specific skill under `.agents/skills/` when available. Examples: `pharma-ledger-integrity` (double-entry and immutable postings), `pharma-pos-fefo` (batch/expiry and overselling), `pharma-offline-sync` (offline quotas/idempotency), `pharma-supabase-rls` (tenant-bound database security), `pharma-cloudflare-safe-release` (deployment safety), `pharma-rtl-enterprise-ui` (Arabic/RTL grid-first UX), and `muslly-commerce-guard` (storefront eligibility/stock/pricing).
- If the relevant skill is missing or another specialized workflow is needed, read `.agents/skills/find-skills/SKILL.md` and follow its process: define a specific query, check the skills.sh leaderboard, search with `npx skills find <topic>`, then review the upstream repository, installation history and skill files before recommending or installing. Prefer trusted publisher-maintained skills; do not bulk-install search results.
- React and rendering-performance tasks may consider the official `vercel-labs/agent-skills` React best-practices skill; PostgreSQL, transactions and RLS tasks may consider the official `supabase/agent-skills` Postgres best-practices skill. They are *candidates*, not assumed present or universally applicable. Follow TanStack Start, Cloudflare and the existing project architecture rather than copying Next.js-only guidance blindly.
- Review source/commands for any newly selected skill and pin versions when practical; install on an isolated branch or developer environment, not by executing unreviewed remote scripts in production. Do not override any existing security, accounting, stock, multi-tenant or public-backend constraints in this file. An instruction file is not evidence of successful implementation, testing or deployment.
- For changes driven by a skill, report the chosen skill, exact changes, validation commands, passing/failing evidence and any blocked follow-up. Require tests before claiming production readiness.
