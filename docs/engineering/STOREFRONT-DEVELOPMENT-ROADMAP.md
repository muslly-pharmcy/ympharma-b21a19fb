# خطة التطوير والمميزات المقترحة

ابدأ بتثبيت الشراء والبيانات والمزامنة قبل توسيع الذكاء الاصطناعي. توجد أصلًا وحدات للولاء وصحة الأسرة والوصفات والمخزون؛ الأولوية لربطها في رحلة مستخدم سليمة بدل تكرار واجهات لها.

## إضافات مرتبة حسب القيمة

| الترتيب | الميزة أو تحسين الميزة القائمة | شرط القبول |
|---|---|---|
| 1 | بحث عربي يتحمل اختلاف الهمزات والأخطاء البسيطة والأسماء التجارية/العلمية | مجموعة بحث مرجعية يقيمها الصيدلي؛ لا يُعامل تشابه الاسم كتكافؤ علاجي. |
| 2 | تنبيه العميل عند توفر صنف يختاره | موافقة مسبقة وإلغاء اشتراك، ومعلومة توفر حديثة مرتبطة بالفرع. |
| 3 | تتبع واضح للطلب وإشعارات واتساب موثوقة عبر outbox | كل حالة محفوظة ومراجَعة، مع إعادة محاولة ومنع الإرسال المكرر، وتمييز الدفع عن التجهيز والصرف. |
| 4 | إعادة طلب الأدوية المزمنة وطلب تجديد الوصفة | اعتماد صيدلي وصلاحية الوصفة؛ لا إعادة صرف تلقائيًا. |
| 5 | موافقة موثقة على البديل الدوائي | الصيدلي يعتمد البديل والسبب والتكلفة؛ موافقة العميل وسجل تدقيق. |
| 6 | عرض توفر الفروع وحجز مؤقت قبل التأكيد | اتفاق ERP على الفرع والوحدة والحجز ومنع البيع المزدوج؛ اختبار التزامن والاسترداد. |
| 7 | استكمال الملف الأسري وتنبيهات مواعيد العلاج | موافقات منفصلة لكل ملف وصلاحيات واضحة، وعدم مشاركة بيانات الأسرة عبر الجهاز أو الحساب. |
| 8 | مراجعة الوصفة المصورة مع إبراز الحقول غير المؤكدة | OCR يعرض الثقة لكل حقل، واعتماد بشري قبل إدخاله في قرار أو طلب. |
| 9 | حفظ مسودة طلب عند ضعف الشبكة | اختيار صريح للمستخدم وحماية بيانات الجهاز؛ لا يُعتبر الطلب مؤكدًا قبل رد الخادم. |
| 10 | قياس رحلة الشراء وأسباب الانقطاع | مقاييس بحث/نتيجة/سلة/تأكيد مرتبطة بأخطاء التشغيل، دون أسماء أدوية أو مرضى في أدوات التحليل العامة. |

لا تضف الدفع الإلكتروني أو توصيات علاج مستقلة قبل اتساق الأسعار وحالة الطلب والتحقق الصيدلي. لا تعرض «آمن» عندما تكون قاعدة المعرفة ناقصة أو غير متاحة.

## آلية العمل

**بيئات منفصلة:** تطوير محلي ببيانات اصطناعية، وتجربة متصلة بقاعدة مستقلة، وإنتاج. لكل بيئة عنوان Supabase وأسرار وإصدار واضح. لا تنسخ بيانات المرضى إلى التجربة دون إجراء مناسب لإخفاء الهوية.

**تغيير صغير قابل للمراجعة:** لكل تغيير مشكلة محددة، وسبب، ومعيار قبول، واختبار يفشل قبل الإصلاح وينجح بعده عندما تكون المخاطر فعلية، وخطة نشر وتراجع. تُراجع تغييرات الدواء سريريًا وتغييرات المال والمخزون على مستوى المعاملة.

**بوابات آلية:** تثبيت frozen lockfile، TypeScript، lint، وحدات، اختبارات PostgreSQL للمعاملات والصلاحيات، audit، بناء، ثم Playwright على سطح المكتب والجوال. استخدم إعدادات خادم فقط في إحدى تجارب المتصفح لضمان أن غياب Vite لا يكسر bootstrap مجددًا. يجب أن تفشل بوابة المتصفح إذا بقي التطبيق هيكل HTML بلا تفاعل.

**اختبارات البيانات الفعلية:** لا يُعتمد تخطي اختبارات RLS كنجاح أمني. البيئة التجريبية يجب أن تختبر مستخدمين ومؤسستين، الخروج والدخول، وتبديل الهوية، ومحاولات الوصول إلى طلب أو وصفة غير مملوكة، وإلغاء الحجز وتكرار الطلبات وتغير الأسعار.

**عقود واضحة:** مصدر واحد لسعر البيع، وحالات منشور/قابل للبيع موحّدة، وعقد ERP مرقّم بإصدارات، ووحدة قياس أساسية محددة، وواجهات تعيد error عند الفشل لا بيانات فارغة ناجحة. لا تغيّر الصلاحيات إلى service_role لإخفاء عطل RLS.

**إصدار قابل للتتبع:** راجع فرق الترحيل، وأنشئ نسخة استعادة، وانشر نفس artifact المفحوص، وسجّل commit وإصدار المخطط. افحص بعد النشر health وظهور منتج وتفاعل زر وتسجيل الدخول وطلب اختبار معتمد، ثم راقب نسبة الأخطاء.

**مراقبة مستقلة:** فحص دوري خارجي للنطاقين وhealth ومسار المتجر. سجلات بمعرّف تتبع مع حذف الأسرار والبيانات الصحية؛ تنبيه لمسؤول واضح وخطة استجابة. راقب نسب فشل تحميل الكتالوج والدخول والتسعير والتأكيد، وعمر طوابير ERP وواتساب.

**صيانة أسبوعية:** تحديثات تبعيات عبر PR واختبارات، ومراجعة التحذيرات ذات الصلة بالإنتاج. لا تعطل قاعدة minimum-release-age لتثبيت إصدار حديث بلا مراجعة. اختبر استعادة نسخة احتياطية دوريًا وراجع صلاحيات الفريق والأسرار.

## تسلسل التنفيذ

- المرحلة الأولى: تطبيق حزمة الإصلاح على التجربة، واعتماد السيناريوهات السريرية والمالية ثم إطلاق مراقَب.
- المرحلة الثانية: إكمال عقد ERP والوحدات والفروع والإلغاء، ثم مزامنة تجريبية ومطابقة يومية قبل التفعيل.
- المرحلة الثالثة: البحث وتنبيهات التوفر وتتبع الطلب، مع قياس التحويل والشكاوى.
- المرحلة الرابعة: تجديد الوصفات والبدائل والملف الأسري بعد اختبار الصلاحيات وموافقة الصيدلي.

تُقدَّر المدد بعد تحديد حجم الفريق وواجهات ERP وخدمة الرسائل. معيار الانتقال هو اجتياز الفحوص والاعتماد، وليس مرور عدد ثابت من الأسابيع.
