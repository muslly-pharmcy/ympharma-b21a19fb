# التقرير الأمني — YmPharma

**تاريخ المراجعة:** 2026-10-10  
**الحكم:** توجد ضوابط حقيقية للمصادقة وRLS وRBAC، لكن المشروع غير جاهز أمنياً للإنتاج قبل معالجة النتائج الحرجة أدناه واختبارها على قاعدة معزولة. هذا تقرير مراجعة شيفرة ومخطط؛ لم تُنفذ محاولة استغلال على بيانات حية.

## الصلاحيات والـRLS

مراجعة مخطط Supabase وجدت RLS مفعلاً على 375 جدولاً في المخططات التي جرى جردها (299 في `public`، و66 في `ym`، و10 في `ym_private`). لم يكن `FORCE ROW LEVEL SECURITY` مفعلاً على أي منها في ذلك الجرد. هذا وحده ليس إثبات ثغرة؛ مالك الجدول وأدوار الخدمة يمكن أن تتجاوز RLS عادة، لذا يجب مراجعة كل استعمال لـservice-role وكل دالة `SECURITY DEFINER`.

نظام `session.server.ts` ينشئ actor ويعرّف صلاحيات، والسياسات في عدة migrations تقيد الصفوف بعضوية المؤسسة. لكن التنفيذ ليس موحداً: `Actor.branchId` يأخذ أول عنصر من `branch_scope` ولا يظهر حارس نطاق فرع شامل. بعض الوظائف تفحص المؤسسة وتقبل `branch_id` دون التحقق من نطاق العضو. كما تختلف أسماء صلاحيات الخادم عن SQL في مسارات المخزون والشراء.

## نتائج عالية الأهمية

### S-01 — عزل مؤسسة التأمين غير مضمون في تحديثات service-role

`src/lib/insurance.mutations.functions.ts` يستخدم عميل service-role. عمليات تحديث provider/plan/insurance تعرض شرطاً على `id` فقط ولا تضيف `organization_id` أو تتحقق من كل العلاقات المرتبطة. مستخدم يملك `insurance.write` في مؤسسة قد يمرر معرّف سجل تابع لمؤسسة أخرى. هذا خلل محتمل cross-tenant مستنتج مباشرة من شرط الاستعلام، ولم يُختبر ضد قاعدة بيانات. **الإجراء:** شرط المؤسسة والعلاقات في كل update، ثم اختبار رفض بين مؤسستين.

### S-02 — تعديل مخزون الإدارة يتجاوز القيود الذرية

`src/lib/store-admin.functions.ts` يقرأ الدفعات ثم يحدث `qty_on_hand` مباشرة، بلا قفل أو إدراج stock movement ولا شرط `qty_on_hand >= qty_reserved`. يمكن أن يبقى الحجز أكبر من الرصيد أو يحدث سباق بين عمليتين. **الإجراء:** قصر التعديلات على RPC ذري موثوق واختبار التزامن والقيود.

### S-03 — checkout يستدعي RPC غير متاح للدور الجاري

`storefront.functions.ts` يستدعي `checkout_cart_fefo` عبر جلسة المستخدم، بينما migration الأحدث تسحب `EXECUTE` من `authenticated` و`anon` وتمنحه لـ`service_role`. النتيجة المتوقعة هي رفض الصلاحية بعد تطبيق سلسلة الترحيلات. **الإجراء:** تصميم مسار خادم يحقق هوية/عضوية المستخدم داخلياً، وعدم إعادة grant عام قبل تحقق أمني واختبار rollback.

### S-04 — صلاحيات `po_receive` و`SECURITY DEFINER`

تعريف `po_receive` يمنح التنفيذ لـ`authenticated`، لكن جسم الدالة لا يثبت بما يكفي هوية المستدعي أو المؤسسة أو صلاحية الممثل قبل اعتماد `p_actor`. حماية Server Function لا تمنع استدعاء RPC مباشراً إذا كان دور قاعدة البيانات يسمح بذلك. **الإجراء:** التحقق داخل الدالة أو قصر EXECUTE على service-role مع وسيط server موثوق، وإضافة اختبار رفض direct RPC وcross-org.

### S-05 — صلاحيات DLQ تحتاج migration قبل الإنتاج

`public.agent_events_dlq_stats()` ذات `SECURITY DEFINER` كانت تسمح بمسار قراءة لا يفرض حارس مدير داخل الدالة، مع grant للمستخدمين المصادقين. PR #14 يضيف شرط `service_role` أو `_intel_can_manage()` ويرفض خلاف ذلك، ويسحب التنفيذ من `PUBLIC/anon`. الـPR مفتوح، migration غير مطبق على قاعدة Supabase، لذلك تبقى المشكلة قائمة حتى مراجعة/تطبيق منفصل واختبار فعلي.

### S-06 — idempotency غير ذريّة

`src/lib/idempotency.server.ts` ينفذ check ثم الأثر ثم insert. يمكن للطلبين المتزامنين استخدام المفتاح قبل أن يكتب الأول السجل. **الإجراء:** قيد/عملية ذرية قبل الأثر مع إعادة response ذاتها، واختبار race.

## API والمعلومات الحساسة

- واجهات ERP العامة تستخدم HMAC ومفاتيح idempotency في handler؛ الاختبارات الحالية تغطي helpers وتوقيعاً/تحويلاً، لا تشغيل queue/ack داخل قاعدة فعلية.
- التقاط الوصفة وOCR موجودان، لكن OCR يعيد نتيجة للعرض ولا يربطها بوصفة منظمة أو قرار صيدلي مسجل. يلزم حفظ provenance وconfidence ومراجعة بشرية قبل أي صرف.
- `medical_vault_files` والملفات الصحية تتطلب اختبارات أدوار وملكية ومؤسسة وstorage path، إضافة إلى سياسة retention واسترجاع.
- `/ai-chat` منفصل عن Agent Runtime ويعرض أرقاماً ثابتة. يجب وسمه demo أو ربطه بخادم حقيقي كي لا تُفهم المخرجات كبيانات تشغيل.
- لم تُعرض مفاتيح أو أسرار في هذا العمل. لم تُجرَ مراجعة كاملة لكل إعدادات secret-management، ولذلك لا يُستنتج من ذلك أن إدارة الأسرار مكتملة.

## سلامة المال والدفتر

`billing_ledger` يعرف حقولاً مثل `entry_type` و`amount_yer` و`notes`، بينما استعلام `modules.functions.ts` يطلب `direction` و`category` و`amount_cents` و`description`. هذا schema drift قد يحول أخطاء القراءة إلى قائمة فارغة. لا توجد بنية محاسبة مزدوجة أو ضمان debit=credit أو settlement/refund متكامل موثق. Checkout أيضاً لا يسجل دفعاً إلكترونياً أو قيد POS. لذلك لا تُستخدم الأرقام المعروضة كدفتر مالي معتمد قبل إصلاح العقد والاختبارات.

## الضوابط الحالية وأدلة الاختبار

توجد مصفوفة صلاحيات في `session.server.ts`، وسياسات RLS في migrations، وسجل audit خلفي، واختبارات وحدات لبعض قرارات RBAC وHMAC وقراءة نصوص SQL. لكن اختبارات `security-grants-regression.test.ts` قد تُتخطى حين لا تتوفر قاعدة PostgreSQL. لم تُشغّل اختبارات عزل مؤسسة/فرع على قاعدة اختبار في هذا التدقيق.

## التوصيات الأمنية حسب التسلسل

1. معالجة S-01 إلى S-05 قبل أي بيانات إنتاجية أو ترقية إصدار، مع اختبارات سلبية فعلية على Supabase محلي/Preview.
2. إضافة حارس نطاق فرع موحد وتوحيد أسماء permissions بين SQL والخادم.
3. جعل idempotency والكتابة المالية/المخزون ذرية، وربط كل أثر بسجل audit دائم.
4. إنشاء قاعدة اختبار في CI لتشغيل RLS والمنح والترحيلات، بدلاً من قبول `describe.skip` كدليل.
5. مراجعة الملفات السريرية وHITL والتقارير والدفع على أساس أقل امتياز، وإظهار الأخطاء بدلاً من استبدالها ببيانات فارغة.
